title: Pulses with Agents
description: Learn how recurring scheduled work can run through a named Agent and its current role, context, and permitted resources.
---

A Pulse can be connected to an **Agent** when recurring work should run through a consistent AI role. Choose the Agent in the Pulse's **Connected to** setting.

The Pulse provides the schedule and **Prompt**. The [Agent](/agents/index) provides the reusable role, durable instructions, context, and permitted resources available at run time.

## Why connect an Agent?

Use a Pulse connected to an Agent when the recurring job benefits from a stable operating role.

Examples include:

- a Sales Reporting Agent preparing a weekly pipeline review
- a Recruiting Agent reviewing open hiring activity
- a Support Agent checking recurring support signals
- an Operations Agent preparing a scheduled operational summary

The Agent gives the recurring work a consistent way of operating across runs.

## Create a Pulse connected to an Agent

  <Step title="Choose the recurring job" icon="file-text">

  </Step>
  <Step title="Choose the Agent" icon="bot">
    Under **Connected to**, select the named Agent whose role matches that recurring work.
  </Step>
  <Step title="Choose the schedule" icon="clock">

  <Step title="Review the Agent’s access" icon="shield-check">

  </Step>
  <Step title="Confirm creation" icon="check-circle">

  </Step>
</Steps>

## The Agent stays live

A Pulse connected to an Agent does not freeze the Agent as it existed on the day the Pulse was created.

When the Pulse runs, the current Agent configuration and live workspace state matter.

That can include:

- Agent instructions
- Agent context
- available [Skills](/skills/index)
- approved [Integrations](/connect/index)
- Group permissions
- provider-side permissions
- current external data

Changes to those resources can affect future Pulse runs.

## Integrations still follow permissions

A Pulse connected to an Agent can use Integrations available to that Agent when the current permissions allow it.

The schedule itself does not create access.

For example, a weekly Sales Pulse can only use the CRM if the relevant CRM Integration is available to the Agent and the connected account has the required provider permissions.

[Learn about giving Agents access to Integrations →](/agents/connections)

## Skills can shape the recurring method

An Agent may have access to [Skills](/skills/index) that help with the scheduled task.

For example, a Reporting Agent could use a reusable reporting Skill when that Skill is available in its current scope.

The Pulse still defines the Prompt and timing. The Skill supplies the reusable task method.

## Agent vs Track

A Pulse can be connected to either, but they solve different needs.

| Connected to | Use it when |
| --- | --- |
| **Agent** | The recurring work should run through a named role and its operating context |
| **Track** | The recurring work belongs to one ongoing body of work and its Track context |

A Pulse can also run without being connected to either. It still runs, but writes no updates.

[Learn about creating a Pulse →](/pulses/creating-a-pulse)

## Consequential actions still require confirmation

Running through an Agent does not bypass Giga’s normal confirmation rules.

If a scheduled run reaches an action that requires confirmation, such as sending an external message, sharing a file, granting access, deleting an important record, or making a payment, the applicable confirmation rule still applies.
