---
title: Creating a Pulse
description: Learn how to create recurring scheduled work with the right Prompt, schedule, and optional Agent or Track.
---

Create a **Pulse** when you want Giga to perform work automatically on a recurring schedule.

Before creating one, decide 3 things: **what should run, when should it run, and what should it be connected to?**

To create one, go to **Cloud → Build & Automate → Pulses**.

## Start with the recurring job

Write the Pulse **Prompt** around the result you want each time it runs.

Good examples:

- review the latest pipeline changes and summarize anything important
- check this Track for new developments and prepare an update
- run a weekly customer health review
- review current recruiting activity and surface open issues

Keep the Prompt durable enough to make sense on future runs.

## Choose what it's connected to

The **Connected to** setting is the Agent or Track the Pulse runs as and writes updates to. A Pulse can currently be connected to:

- an [Agent](/agents/index)
- a [Track](/tracks/index)
- nothing

Choose based on where the recurring work belongs.

| Connected to | Use it when |
| --- | --- |
| **Agent** | The recurring work should run through a named AI role |
| **Track** | The work belongs to one ongoing body of context |
| **Nothing** | The Prompt can stand on its own. The Pulse still runs, but writes no updates |

> **Choose the connection deliberately**
>
> What a Pulse is connected to shapes the context available to the scheduled run. Use the live workspace to select the actual Agent or Track.

## Choose a schedule

The current Pulse model supports 2 scheduling approaches under **When it runs**.

  <Card title="Saved times" href="/pulses/schedules" icon="calendar">
    Attach the Pulse to one or more reusable named times, like “Morning”, already available in the workspace.
  </Card>
  <Card title="Its own schedule" href="/pulses/schedules" icon="clock">
    Give the Pulse its own daily, weekly, monthly, or intra-day cadence.

The exact Saved times come from the current workspace rather than a fixed global list.

## Create the Pulse

<Steps>
  <Step title="Name the Pulse" icon="file-text">
    Use a clear name that describes the recurring job.
  </Step>
  <Step title="Write the Prompt" icon="edit-3">
    Explain what Giga should do each time the Pulse runs.
  </Step>
  <Step title="Choose the schedule" icon="clock">

## Writing a useful Pulse Prompt

A good Pulse Prompt should tell Giga what outcome matters each time it runs.

For example:

> Review the latest activity for this Track. Summarize material changes, unresolved issues, and anything that needs attention. If nothing meaningful changed, keep the update brief.

Useful Prompts can include:

- what to check
- what counts as meaningful
- what output to produce
- which conditions should be surfaced
- what to avoid
- when human confirmation is still required

Avoid Prompts that depend on a one-time detail that will stop making sense next week.

## Pulse connected to an Agent

Choose an Agent when recurring work benefits from a reusable role.

For example, a **Weekly Sales Review** Pulse could be connected to a Sales Reporting Agent.

The Agent contributes its role, durable instructions, context, and permitted resources at run time.

[Learn about Pulses with Agents →](/pulses/with-agents)

## Pulse connected to a Track

Choose a Track when recurring work belongs to one ongoing effort.

For example, a **Customer Renewal Check** Pulse could be connected to the customer’s renewal Track and ask Giga to surface meaningful changes on a recurring cadence.

The Pulse uses the Track context available when it runs.

Track visibility and access continue to follow the Track’s [Group](/groups/index).

## Pulse that isn't connected

A Pulse does not have to be connected to an Agent or Track.

This can be useful when the Prompt is self-contained and does not need a dedicated role or ongoing Track context. It still runs, but writes no updates.

The live run still uses whatever workspace permissions and capabilities are available to it.

## Permissions still apply

Creating a schedule does not grant new access.

When the Pulse runs, Giga still needs the required:

- Integrations
- provider permissions
- Group access
- Agent or Track access
- live tools

If the required capability is unavailable, the scheduled work should not pretend it succeeded.

## Consequential actions still require confirmation

A recurring Prompt does not erase Giga’s normal safety boundaries.

If a Pulse reaches a step that would require confirmation, such as sending an external message, granting access, deleting an important record, or making a payment, the live run should follow the applicable confirmation rule.

## Confirm before creation

Creating a Pulse changes future scheduled behavior.

Giga should confirm the user’s intent before creating it.

The confirmation should make the recurring behavior clear enough that the user understands:

- what will run
- the schedule
- the Agent or Track it's connected to, if any

## A simple example

Imagine creating a **Weekly Customer Health Review** Pulse.

| Setting | Example |
| --- | --- |
| **Name** | Weekly Customer Health Review |
| **Prompt** | Review current customer signals and summarize meaningful changes, risks, and open issues |
| **Schedule** | Weekly |
| **Connected to** | Customer Success Agent |

At each run, Giga uses the current Agent configuration, live Integrations, and permissions rather than relying on a frozen snapshot from the day the Pulse was created.
