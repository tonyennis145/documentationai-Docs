A **Connection** gives Giga access to an external tool or system so it can work with live company information and, where permitted, take action there.

Connections can represent apps, APIs, databases, browser sessions, MCP servers, and other connected services.

## Connect from Chat or manage Connections directly

You do not always need to leave a [Chat](/chats/index) to start connecting something.

When the connection flow supports it, you can tell Giga what you want to connect and Giga can start the secure setup flow from the Chat.

You can also manage your Connections from the Connections area in Giga.

[Learn how to connect a tool →](/connections/connect-a-tool)

## How Giga connects

Different services support different connection methods.

| Connection method       | Typical use                                                                                            |
| ----------------------- | ------------------------------------------------------------------------------------------------------ |
| **MCP**                 | A service exposes an MCP server that Giga can connect to                                               |
| **OAuth**               | A service supports delegated account access through OAuth                                              |
| **API key or PAT**      | The service uses a user-provided key or personal access token                                          |
| **Database connection** | Giga connects to an external database using stored credentials                                         |
| **Browser session**     | Giga needs to interact with a website directly when another connection method cannot complete the task |

For new or custom integrations, Giga’s operating guidance prefers the strongest self-serve path available in this order:

1. **MCP**
2. **OAuth** when a supported self-serve OAuth flow is available
3. **API key or PAT**
4. **Browser login**

The exact method depends on the service and the connection mechanisms it actually supports.

## Connections stay permission-aware

A Connection does not automatically give every person or every piece of work access to the same systems.

Giga checks the live workspace state to determine:

- which Connections you can access
- which credentials are yours
- which credentials have been shared into a [Group](/groups/index) you belong to
- which actions the connected service allows
- which tools are currently exposed in your session

> **Live access is the source of truth**
>
> Giga should inspect the current workspace and connection state rather than assuming a service is connected or that a user has permission to use it.

## Secrets stay out of Chats

Credentials are stored securely and used through Giga’s connection layer.

Giga should never ask you to paste passwords, API keys, tokens, OAuth secrets, or database connection strings into a normal Chat when a secure connection flow is available.

For services that require a user-provided secret, Giga can direct you to the appropriate secure setup flow.

> **Keep credentials in the secure connection flow**
>
> Secrets should not be written into Chats, [Context Notes](/tracks/context-notes), or files.

## How Giga uses a Connection

Once a Connection is available, Giga should use the connection mechanism designed for that service instead of asking you to manually move data between systems.

For example:

- a connected API can be queried directly
- a connected database can be queried without exposing its connection string
- an MCP service can expose its own tools to Giga
- a browser session can be used when direct website interaction is required

This lets a [Chat](/chats/index), [Agent](/agents/index), or [Workflow](/workflows/index) work with live systems while keeping the underlying credentials protected.
