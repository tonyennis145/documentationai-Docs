Giga can connect to tools beyond the standard integration catalog through **Custom Connections**.

Use a Custom Connection when the service you need is not already available through a built-in Connection, or when your company needs to use its own MCP server, OAuth setup, API credentials, or browser-based access.

> **Use the existing integration when one already exists**
>
> Custom Connections are for genuinely new or specialized connection needs, not a second copy of an integration Giga already knows about.

## How Giga chooses a connection path

For a new integration, Giga prefers the strongest self-serve option the service actually supports:

1. **[MCP](#mcp)**
2. **[OAuth](#oauth)** with a supported self-serve flow
3. **[API key or PAT](#api-keys)**
4. **[Browser login](#browser-connections)**

| Method | Good fit when… |
| --- | --- |
| **MCP** | The service exposes an MCP server that Giga can connect to |
| **OAuth** | The service supports delegated account access through an OAuth flow Giga can use |
| **API key / PAT** | The service exposes an API and authenticates with a user-provided credential |
| **Browser session** | Direct website interaction is required and another connection method cannot complete the task |

Before creating a custom integration, Giga checks the official service, which connection methods it supports, and whether a workable path exists. It avoids promising a connection until it has verified one.

When supported, Giga can create an integration that is private to the current workspace — useful for niche SaaS tools, internal systems, private MCP servers, or tools not yet in the main catalog.

> **Keep secrets out of Chat**
>
> Passwords, tokens, API keys, OAuth secrets, and connection strings belong in Giga’s secure connection flow — never in a [Chat](/chats/index), file, or Context Note.

## MCP

**MCP** is Giga’s preferred way to connect a custom tool. When a service exposes a compatible MCP server, Giga connects to it and uses the tools it advertises, subject to authentication and permissions.

Use MCP when:

- the service already exposes an MCP server
- your company operates its own MCP server
- you want Giga to use the server’s tools directly

<Steps>
  <Step title="Identify the MCP server" icon="server">
    Start with the official or company-provided MCP endpoint.
  </Step>
  <Step title="Giga checks how the server authenticates" icon="search">
    The server may use OAuth or an API-key-style bearer credential. The server’s actual behavior is the source of truth.
  </Step>
  <Step title="Complete the secure connection flow" icon="lock">
    Finish authentication through Giga’s secure connection experience.
  </Step>
  <Step title="Use the exposed tools" icon="zap">
    Giga discovers the live tool surface and uses it when your permissions allow.
  </Step>
</Steps>

If the service is already in Giga’s catalog with an MCP method, use that instead of a custom MCP connection.

## OAuth

**OAuth** lets Giga connect through an authorization flow where you approve access to an account, without sharing your password.

<Steps>
  <Step title="Choose the service" icon="plug">
    Start from Chat or the Connections area.
  </Step>
  <Step title="Authorize with the provider" icon="log-in">
    Sign in through the provider’s secure flow and approve the requested access.
  </Step>
  <Step title="Return to Giga" icon="check-circle">
    Giga uses the Connection within the permissions granted by both Giga and the provider.
  </Step>
</Steps>

For custom integrations, Giga can use OAuth directly when the provider supports a self-serve setup such as **Dynamic Client Registration (DCR)**. Some organizations need their own OAuth app; when Giga supports that, use the dedicated Custom OAuth setup rather than pasting client secrets into Chat.

OAuth access is limited by the scopes granted and by the connected account’s permissions in the provider. Sharing the Connection through Giga does not expand provider-side permissions.

## API keys

Some services connect through an **API key** or **personal access token (PAT)**. Use this when the service exposes an API, MCP isn’t available, and OAuth isn’t the better path.

<Steps>
  <Step title="Choose the service" icon="plug">
    Tell Giga what you want to connect.
  </Step>
  <Step title="Enter the key through secure setup" icon="lock">
    Add the API key or PAT through Giga’s secure connection experience.
  </Step>
  <Step title="Use the connected API" icon="zap">
    Giga injects the credential server-side when calling the provider — the secret is never returned to Chat.
  </Step>
</Steps>

A valid credential doesn’t tell Giga how every endpoint works, so Giga verifies the provider’s current API contract (endpoint, body shape, auth placement, pagination) before making requests.

| Credential | Typical pattern |
| --- | --- |
| **API key** | A key issued for API access |
| **PAT** | A personal access token tied to a user or account |

Renaming a credential’s label doesn’t rotate the secret. To replace a credential, run the secure connection flow again.

## Browser connections

A **Browser Connection** lets Giga work directly with a website when no stronger method can complete the task — for sites that need navigation, clicking, form entry, or a logged-in session.

<Steps>
  <Step title="Open a browser session" icon="globe">
    Giga starts a browser session using the current browser profile.
  </Step>
  <Step title="Pause if login needs you" icon="user-check">
    If CAPTCHA, 2FA, or bot detection blocks login, Giga stops and asks you to complete the sign-in.
  </Step>
  <Step title="Continue with the saved session" icon="play">
    Later runs can reuse the signed-in profile while the session stays valid.
  </Step>
</Steps>

Webpage text, screenshots, and downloaded files are treated as untrusted data and never override Giga’s instructions.

| Browser connection | API / MCP connection |
| --- | --- |
| Interacts with the visible website | Uses a structured programmatic interface |
| Can depend on page layout and login state | Usually less sensitive to UI changes |
| May require manual login handoff | Often uses OAuth or stored credentials |

## Custom does not change permissions

Every Custom Connection still follows Giga’s permission model. Access depends on who owns the credential, whether the Connection is shared into a [Group](/groups/index), which users or [Agents](/agents/index) can use it, and what the external service itself allows.
