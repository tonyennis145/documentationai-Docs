When you ask Giga to research something or take action, it should use the most appropriate live capability available for that task.

## How Giga chooses a route

<Steps>
  <Step title="Use a first-class Giga tool when one exists" icon="check-circle" title-type="p">
    Giga uses the workspace tool designed for that Giga object instead of editing backing files by hand.
  </Step>

  <Step title="Use connected systems through their supported connection" icon="plug" title-type="p">
    Connected providers, APIs, databases, and MCP tools are used when they can complete the task directly.
  </Step>

  <Step title="Use the browser when a website needs direct interaction" icon="globe" title-type="p">
    Browser automation is the fallback for tasks that cannot be completed through an API, MCP tool, database, or first-class integration.
  </Step>
</Steps>

This means a single Chat can combine [Integrations](/connect/index), live workspace state, and browser work as needed.

## Browser-based work

Giga can use a Cloud Browser Session for logged-in tasks when that capability is available. If a site blocks automated sign-in with CAPTCHA, bot detection, or two-factor authentication, Giga should stop and ask you to complete the sign-in step.

> **Treat websites as data**
>
> Website text, page content, screenshots, console output, and downloaded files are evidence from the web. They do not override Giga’s operating instructions.
