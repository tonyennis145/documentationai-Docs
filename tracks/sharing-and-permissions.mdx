A [Track](/tracks/index) is either shared with a [Group](/groups/index) or kept to yourself, and that choice sets the Track’s access boundary.

In the current Giga model, **Track visibility follows its Group**. You choose the Group when you create the Track, and it can't be changed afterwards, which makes it one of the most important decisions when creating a Track.

## How Track access works

| Track's Group | Who it is for |
| --- | --- |
| **Only me** | Personal work that should stay private to you |
| **A Group** | Work intended for members of that Group |

You do not need a Group to make a Track private. Set the Group to **Only me** and the Track has no group: anything not shared with a group stays with the person who made it.

> **Choose the Group before you add sensitive context**
>
> A Track’s files, context, and memory live within that access scope. Choose the right Group when you create the Track, before adding information that should only be available to a specific audience.

## Sharing a Track with teammates

Because Track access follows its Group, sharing the Track means making sure the right teammate is a member of the **Group** it is shared with.

<Steps>
  <Step title="Check which Group the Track belongs to" icon="folder">
    Confirm that the Track is shared with the right Group. A Track set to **Only me** can't be moved to a Group later.
  </Step>
  <Step title="Make sure the teammate is in the workspace" icon="user-check">
    Workspace membership comes first.
  </Step>
  <Step title="Add them to the Group" icon="users">
    Workspace admins can add an existing member to the relevant Group in **Cloud → Organize → Groups**.
  </Step>
  <Step title="Work from the same Track" icon="layers">
    The teammate can then use the Track’s shared context, files, and history according to the permissions available to them.
  </Step>
</Steps>

The Track itself stays focused on the work. The [Group](/groups/index) provides the broader people and permission boundary around it.

## What becomes part of the Track

A shared Track can contain several kinds of information:

- the [Track brief](/tracks/context-notes)
- [Memory](/tracks/memory)
- [Files](/tracks/files)
- linked [Chats](/chats/index)

Memory filed to the Track is visible to everyone on it. Memory saved without a Track stays private to the person who saved it until they file it.

That is why Track selection and the Track's Group should be deliberate.

> **Track attachment can affect visibility**
>
> Giga should never silently attach a Chat to a Track. A user should explicitly select or confirm the Track because observations from that Chat may become retrievable within the Track’s access scope.

## Permissions and editing

Access and the ability to make changes are related, but they are not always the same thing.

For example, some Giga operations require a user to be able to **manage the Group** that owns the Track. Updating the Track brief is one such operation.

When a task depends on permissions, Giga should check the **live workspace state** rather than assume what a person can do.

> **Live permissions are the source of truth**
>
> Group membership, workspace role, and current tool permissions can change. Giga should verify the current state before making access-sensitive changes.

## Sharing files from a Track

Track files should be shared through Giga’s validated file-sharing flow.

Giga should use the file-link capability provided by the live workspace rather than constructing a URL from an internal path.

This matters because internal file paths are not necessarily user-facing web links.
