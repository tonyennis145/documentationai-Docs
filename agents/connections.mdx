[Integrations](/connect/index) let an Agent work with live external tools and systems.

An Agent might use a CRM, support platform, analytics tool, database, MCP server, or browser-based service when that Integration is available within its current permission scope.

## Access is permission-aware

An Agent should only use an Integration when the live Giga environment says it is available.

Several layers can affect that:

| Layer | What it controls |
| --- | --- |
| **Agent placement** | The Group and scope the Agent operates within |
| **Group membership** | Who can access the Agent and shared resources |
| **Integration sharing** | Whether the credential or Integration is available in that scope |
| **Credential ownership** | Who can manage or remove the underlying credential |
| **Provider permissions** | What the connected external account can actually do |
| **Live tool surface** | Which actions the Integration currently exposes |

> **Existing in the workspace is not enough**
>
> An Agent should never assume it can use every Integration simply because that Integration exists somewhere in Giga.

## How to give an Agent access

The exact controls can vary with the current product surface, but the access model is consistent.

<Steps>
  <Step title="Start with the Agent’s job" icon="user">
    Identify which external systems the Agent genuinely needs for its role.
  </Step>
  <Step title="Check the Agent’s Group" icon="users">
    Confirm the Agent sits in the permission scope intended for that work.
  </Step>
  <Step title="Make the Integration available in the right scope" icon="plug">
    Use the current Giga sharing and Agent configuration controls to make the approved Integration available.
  </Step>
  <Step title="Confirm provider permissions" icon="shield-check">
    Check that the connected external account can perform the actions the Agent needs.
  </Step>
  <Step title="Use the live Integration" icon="zap">
    The Agent can use the tools exposed by that Integration when the current session allows it.
  </Step>
</Steps>

## Share the narrowest useful access

Give an Agent the Integrations required for its role rather than every company Integration.

For example:

- a **Sales Research Agent** may need the CRM and approved research tools
- a **Support Agent** may need the support platform and customer systems
- a **Finance Agent** may need approved financial data sources

Keeping access focused makes the Agent easier to reason about and keeps the permission boundary aligned with its actual job.

## Shared Integration vs owned credential

An Integration can be usable by an Agent or teammate without transferring ownership of the credential behind it.

The credential owner may retain management controls such as renaming, rotating, or deleting the credential.

The Agent uses the Integration through Giga’s secure connection layer. It does not need the raw secret.

[Learn about Sharing Integrations →](/connect/sharing)

## Secrets stay out of Agent instructions

Do not place passwords, API keys, access tokens, OAuth secrets, or database connection strings in:

- [Agent instructions](/agents/instructions)
- Agent context
- [System Instructions](/library/context-cards)
- files
- normal Chats

Secrets belong in the secure Integration flow.

> **Integrations carry access. Instructions carry behavior.**
>
> Keep authentication in Giga’s secure connection layer and keep the Agent’s durable instructions focused on how it should work.

## Provider permissions still apply

Giving an Agent access to an Integration does not expand the permissions of the external account.

If the connected account is read-only, the Agent remains limited to read-only actions through that Integration.

If the provider exposes only certain tools, Giga should use the live tool surface rather than assume broader capabilities.
